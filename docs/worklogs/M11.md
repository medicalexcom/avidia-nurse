# M11 — Stateful patient simulation and virtual clinical engine

Date: 2026-08-14. Builds on M10 (`8d4e54a`).

Scope note: M11 adds the blueprint's virtual-patient simulation as a
deterministic, server-authoritative clinical engine. The core principle of
the instruction is absolute and shaped every decision below: THE LLM IS
NOT THE SIMULATION ENGINE. Patient state, action validity, transitions,
critical events, scoring, and outcomes are structured data interpreted by
versioned deterministic code — testable, replayable, and functional with
zero AI configuration. The simulation feeds the ONE existing mastery
model; it does not grow a parallel one.

## What shipped

### The deterministic engine core (spec C/D/E/G — ADR-0028)

`packages/simulation` is a pure rule interpreter:
`applyAction(caseDef, state, action) → { state, events, rejected }`. No
I/O, no randomness, no clock reads — same state plus same action equals
the same result, always. All clinical behavior is data in the case
definition (rules with triggers, conditions, and effects); there are no
per-case code paths and no model inference anywhere in the loop.

### One typed patient state for every case (spec C — ADR-0029)

`PatientState` is a single structured record: versions, phase, simulated
time, true vitals, last observed vitals snapshot, per-finding
`{present, revealed}`, per-lab `{released, value, flag}`, statements,
safety flags, deterioration level, fired-rule ids, pending schedules, the
append-only action log, and the completion record. Cases differ only in
data, never in state shape, so one interpreter, one redactor, and one
persistence column serve the whole library.

### Explicit phases and simulated time (spec D/H)

Sessions move through explicit phases via rule effects, and time is
explicit simulation time: every action carries an authored minute cost,
`wait` advances time deliberately, and time-triggered rules fire in
deterministic order when their minute arrives. Nothing is wall-clock.

### True state versus observed state (spec M)

The vitals a student sees are a snapshot stamped with the minute they
obtained them; the true vitals keep evolving underneath. Reassessment is
therefore a real clinical decision with a real time cost, and the UI
labels a stale set explicitly ("this set is not current. Reassess to
update it.") versus "(current)".

### Hidden findings and the no-leak contract (spec M/N)

Findings carry `present` and `revealed` separately. Focused assessments
(spec M) reveal only present findings in the assessed system; dialogue
answers can be gated on findings being revealed first. The redacted
`clientView` is the ONLY payload a device receives mid-session — revealed
findings only — and server-side column grants make the raw `state` jsonb
unselectable, so hidden content cannot reach the UI, telemetry, or any
client-accessible payload. Invariant tests serialize the client view and
assert unrevealed finding text never appears in it, and the UI tests
repeat the assertion against rendered output.

### Bounded physiology (spec J)

`PHYSIOLOGIC_BOUNDS` (HR 20–220, SpO2 50–100, and so on) clamp every vital
after every effect, intersected with tighter per-effect bounds. No rule
stack, however authored, can produce an impossible vital — enforced by the
interpreter, not by authoring discipline.

### Structured actions and events (spec E/F/I)

The action catalog is controlled and finite: obtain vitals, focused
assessments per system, interventions (oxygen, medications per order),
notify provider, ask the patient (scripted prompts), request labs, wait,
and end-of-scenario actions where authored. Every action submission and
every consequence is a typed event; student-visible events drive the
session feed, hidden events (rule firings, classifications) surface only
in the debrief.

### Rule-defined consequences and outcomes (spec G/AP)

Deterioration, improvement, lab releases, statement changes, and session
endings are all authored rules with explicit triggers (action, time,
condition), conditions over state, and bounded effects. Outcomes are
explicit authored records (stabilized, deteriorated, coded, etc.) reached
only by rules — never inferred.

### Critical and unsafe actions (spec Q/R)

Cases author critical actions (with deadlines where clinically
meaningful) and unsafe-action classifications. Unsafe choices produce
in-simulation consequences and appear in the debrief as "Actions worth
rethinking" — consequences without shaming, per spec R.

### Deterministic scoring on the CJMM (spec O/S — ADR-0032)

`scoreSession` evaluates named criteria across the six NCSBN Clinical
Judgment Measurement Model dimensions, returning a per-entry ✓/✗ ledger
with points, per-dimension subtotals, missed critical actions, and unsafe
actions taken. `SIMULATION_SCORE_VERSION = 1` stamps every score. Nothing
is judged by AI, and the debrief says so.

### One mastery model — evidence normalization (spec T/U)

At completion, in the same transaction as scoring, the score is
normalized into the SAME `PerformanceEvent` shape M8 consumes for
question attempts: per mapped concept, earned/possible across the mapped
dimensions with `EVIDENCE_CORRECT_THRESHOLD = 0.65` deciding correctness,
null confidence, and the centralized ADR-0022 v1 mastery constants.
Concepts with no scoreable mapped points yield NO evidence — silence over
invention. There is no separate simulation mastery.

### The case library (spec A/B/AF — ADR-0030)

Three cases, authored deep rather than wide (quality over quantity, per
spec AF): post-op pulmonary embolism, hypoglycemia, and hyperkalemia.
Every patient is fictional with invented names — no real-person data
(spec B). Each case carries hidden findings, deterioration branches,
unsafe paths with consequences, scripted dialogue, critical actions,
scoring criteria, and concept mappings into the existing knowledge graph.

### The validation gate (spec AB)

`validateCase` is a hard gate before ACTIVE: referential integrity across
every id, physiologic sanity, guaranteed termination (a time-triggered
end is provably reachable by pure waiting), reachability of every
outcome, and honest concept keys resolved against the knowledge catalog.
Seed generation runs the gate, so an invalid case cannot reach the
database at all.

### Scripted dialogue — functional without AI (spec AG/AH/AI — ADR-0031)

"Ask the patient" presents authored prompts mapping to authored,
state-gated responses. No synchronous LLM call exists anywhere in the
action loop (spec BD): submitting an action is one database round-trip,
and the entire feature works with zero AI keys configured.

### SQL as the authoritative runtime (ADR-0028)

Migration `0011` implements the interpreter in plpgsql over jsonb:
`start_simulation`, `simulation_act`, `get_simulation_view`,
`abandon_simulation`, and `get_simulation_debrief` as SECURITY DEFINER
RPCs. The TypeScript engine is the pinned executable specification; the
SQL is what actually runs, because a client-side engine could fabricate
outcomes and mastery evidence. Both carry
`SIMULATION_ENGINE_VERSION = 1`, bumped in lockstep.

### Persistence, resume, and audit (spec V/W/X)

Sessions persist in `simulation_sessions` (state as unselectable jsonb);
every submission — including rejections — appends to
`simulation_actions`, an append-only audit log that replays to the exact
final state (spec W). Resume is server-side: reopening a session calls
`get_simulation_view` and rebuilds the redacted view from authoritative
state (spec X); `start_simulation` returns the existing active session
(`resumed: true`) rather than forking a new one.

### Idempotency and concurrency (spec Y/Z/BC)

`simulation_act` takes an idempotency key per submission attempt;
replaying the same key returns the ORIGINAL stored result, so a
double-tapped "Administer medication" can never administer twice — tested
explicitly in the engine suite, the authz script, and the UI tests.
Concurrent submissions serialize under `FOR UPDATE`, and each action is
one reject-or-apply transaction: no partial state can ever be committed.

### Versioning (spec AX/AY)

Cases carry `caseVersion`, the engine carries
`SIMULATION_ENGINE_VERSION`, scores carry `SIMULATION_SCORE_VERSION`, and
sessions pin the case and engine versions they started under.
`start_simulation` refuses cases whose engine version it does not speak.

### Generated seed with a sync pin (spec AB/AF)

`buildSeedSql()` validates every built-in case and emits migration
`0012_simulation_seed.sql` (dollar-quoted jsonb upserts on `case_key`). A
sync-pin test byte-compares the checked-in migration against a fresh
generation, so library/migration drift is a failing test;
`UPDATE_SIM_SEED=1` regenerates intentionally.

### Security and authorization (spec AW/N)

RLS scopes every read to the owner; the `definition`, `state`, `score`,
and event columns are excluded from client grants entirely. The authz
script gained checks 50–57: User B cannot start against, read, act on, or
view User A's session; anonymous clients get nothing; direct
inserts/updates to session and action tables fail; the mid-session view
is probed for actual hidden case text ('circumoral cyanosis') and must
not contain it; idempotent replay returns identical JSON with one stored
row; the debrief RPC refuses active sessions; and cascade-deletion checks
cover the new tables.

### The client data layer (spec N/V/X/Y)

`apps/app/src/features/simulation/simulationApi.ts` is thin typed
wrappers over the RPCs. The client never computes physiology, validity,
or scores; the only mid-session payload type it knows is `ClientView`
(deep-imported from `@avidia/simulation/src/redact`, following the
`@avidia/assessment/src/mix` precedent so node-only validator modules
never enter the web bundle). `newIdempotencyKey()` mints 16 random bytes
per submission attempt.

### The case library screen (spec AF/X)

`/course/[id]/simulation` lists the active seeded cases with title,
description, difficulty, scenario type, and estimated duration. An active
session surfaces as "Resume simulation"; completed runs link to their
last debrief. Reached from the course detail screen's new "Simulations"
button.

### The patient chart (spec AJ–AO)

`/simulation/[id]` renders a polished chart: patient banner, vitals with
explicit staleness labeling, revealed findings, released labs, medication
orders, the controlled action list with per-action time costs, scripted
dialogue prompt picker, a session event feed, a static nursing-process
hint toggle, and a two-tap abandon ("Tap again to leave without
finishing"). On desktop widths (≥900px) it lays out as three columns —
chart, actions, feed; on mobile it stacks. Completion shows an outcome
banner linking to the debrief.

### The debrief (spec AQ/AR/AS)

`/simulation/[id]/debrief` renders all ten required components: outcome
card with summary and duration; the full score ledger (per-dimension
subtotals, every criterion ✓/✗ with points, and the "nothing is judged by
AI" note); missed critical actions; unsafe actions framed as
consequences; key cues found and missed — hidden information is revealed
here, after completion, where it teaches; a step-by-step timeline replay
including behind-the-scenes rule firings with explanatory metadata
(spec AS); mastery evidence movements ("Pulmonary embolism: 40% → 55%")
with the one-mastery-model note; and deterministic recommendations.

### Telemetry — minimal by design (spec BE)

Exactly four analytics events were added: `simulation_started`,
`simulation_completed`, `simulation_abandoned`, and `hint_used`. No
per-action telemetry, and nothing in any event can carry hidden state.

### Testing: scenarios, branches, properties (spec AZ/BA/BB)

The simulation package carries 10 suites / 107 tests: deterministic
scenario walkthroughs with pinned timings (spec AZ) that both the TS and
SQL engines must reproduce; per-case branch tests covering optimal,
delayed, unsafe, and passive paths to their distinct outcomes (spec BA);
and property/invariant tests — vitals always in bounds, sessions always
terminate under pure waiting, replay always reproduces state, client
views never contain unrevealed text (spec BB).

### UI tests against the real engine

The app-side suite (10 tests) uses the actual engine and actual redactor
to build fixtures, so "hidden findings never render" is tested against
the same contract the server enforces. It covers the library, resume,
start analytics + navigation, no-leak rendering, idempotency-key
submission, stale-vitals labeling, a full optimal-path completion,
two-tap abandon, the full debrief render, and the debrief-unavailable
error path.

### Documentation

Five ADRs: 0028 (deterministic simulation architecture — the LLM is never
the engine), 0029 (patient state representation), 0030 (case definition
format and the validation gate), 0031 (AI boundaries in the simulation),
0032 (scoring and evidence normalization). Plus this worklog.

### What M11 deliberately did not do

No LLM-adjudicated actions, no AI case generation, no client-side engine,
no separate simulation mastery, no per-action telemetry, no XP or
leaderboards bolted onto simulations, and no M12 work. The case library
was kept to three deep cases rather than many shallow ones, per spec AF.
M11 stops here pending its dedicated reconciliation.
