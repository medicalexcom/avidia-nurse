# M2 — Courses, Modules, and Exams

- **Date:** 2026-08-12
- **Status:** Complete
- **Spec basis:** Playbook v2 (§6 data model, §8 security/RLS, §19 milestones), Blueprint v2
  (course structure), founder's written M2 requirements

## Scope delivered

An authenticated student can create courses, add and reorder modules, schedule exams (with an
optional weight) that are associated with the modules they cover, see a live countdown to each
exam, edit and delete everything they created, archive courses instead of deleting them, and
never see or touch another student's data.

### Database (`supabase/migrations/0002_courses_modules_exams.sql`)

- **courses** — id, user_id → profiles (cascade), title (trimmed, 1–120), term (≤60, null),
  institution_name (≤120, null), status (`active`/`archived`, default `active`), timestamps.
- **modules** — id, course_id → courses (cascade), title (1–120), sequence (int, display
  order), timestamps.
- **exams** — id, course_id → courses (cascade), title (1–120), exam_at (`timestamptz`, a UTC
  instant), weight (numeric, null or 0–100), timestamps.
- **exam_modules** — (exam_id, module_id) composite PK, both FKs cascade. Normalized join
  table; no delimited strings anywhere (ADR-0007).
- Indexes: courses(user_id), modules(course_id, sequence), exams(course_id, exam_at),
  exam_modules(module_id). `set_updated_at` triggers reused from migration 0001.

### Row-level security (spec B)

- RLS enabled **and forced** on all four tables.
- courses: select/insert/update/delete only where `user_id = auth.uid()`.
- modules and exams inherit ownership: every policy requires the parent course to belong to
  the caller.
- exam_modules: the INSERT policy joins exams and modules and requires both to be in the
  **same course owned by the caller** — cross-user and cross-course links are rejected by the
  database itself. No UPDATE grant; associations are replaced.
- Column-level grants prevent reassigning `courses.user_id` and `modules/exams.course_id`
  (no reparenting), mirroring the M1 profiles approach.
- `scripts/authz-check.mjs` extended with 16 M2 checks (owner CRUD, cross-user read/write
  denial, reparenting denial, cross-user and cross-course link denial, cascade verification,
  profile survival). Runs against a real project when secrets are present; skips cleanly
  otherwise.

### Domain layer (`packages/domain`, new)

Pure TypeScript, no React, no I/O — created now because M2 gives it real content:

- `validation.ts` — `validateCourse` (title required/trimmed/max-length, term and institution
  optional with caps), `validateModuleTitle`, `validateExam` (valid date required, weight
  optional 0–100, past dates accepted intentionally), `resequence` (gapless module order),
  `moveItem`.
- `time.ts` — IANA-zone-aware conversion built on `Intl`: `zonedDateTimeToUtc` (two-pass
  offset resolution; rejects impossible dates like Feb 30), `parseDateAndTime`,
  `isoToZonedFields`, `formatInZone`, `calendarDaysBetween`, `isValidTimeZone`.
- `countdown.ts` — `examCountdown` returning `Exam in N days` / `Exam tomorrow` /
  `Exam today` / `Exam completed` / `Date unavailable`, computed as a **local calendar-day
  difference** so DST transitions and timezone boundaries cannot skew it; `nextUpcomingExam`.
- 30 unit tests, including DST spring-forward and fall-back (America/Chicago 2026), Chicago
  vs Tokyo boundary cases, invalid inputs, and round-trips.

### Data access (`apps/app/src/features/courses/`)

Repository modules behind which screens do all data access (no scattered supabase-js calls;
a caching layer can slot in behind this boundary in M13):

- `coursesApi.ts` — list/fetch/create/update/archive/unarchive/delete, every query scoped to
  the caller's user id on top of RLS; update sanitizer strips non-updatable fields
  (privilege-escalation attempts are dropped client-side and rejected server-side).
- `modulesApi.ts` — list (by sequence), create, rename, persist order, delete.
- `examsApi.ts` — list/fetch with linked module ids, create, update, replace associations,
  delete; update sanitizer as above.
- 12 unit tests assert owner scoping, sanitizer behavior, and association replace semantics
  against a recorded fake query builder.

### UI (spec D–H)

- **Courses** (`/courses`, now a live destination, placeholder flag removed) — loading, error
  with retry, empty state with "Create your first course", and populated cards showing title,
  term, module count, and the next exam's countdown. Archived courses are hidden behind a
  toggle.
- **Course detail** (`/course/[id]`) — metadata with edit; modules (add, rename, ↑/↓ reorder
  persisted as gapless sequences, delete with inline confirmation); exams (formatted local
  time, countdown, weight, covered modules; tap to edit); archive/unarchive; delete with an
  inline confirmation that states exactly what cascades. Two-column layout ≥900 px wide.
- **Course form** (`/course/new`, `/course/[id]/edit`) and **exam form**
  (`/course/[id]/new-exam`, `/exam/[examId]`) — domain-validated; the exam form takes local
  date/time in the student's timezone (profile timezone, device fallback — shown in the form,
  never hard-coded), converts to UTC on save, prefills edits back in local time, includes
  module checkboxes and a non-blocking past-date notice.
- Screen components live in `src/features/courses/screens/` with thin route files under
  `app/`, so screens are unit-testable without the router. Shared `SecondaryButton` and
  `ConfirmInline` primitives added to `src/ui/components.tsx` (inline confirmation works
  identically on native and web, unlike `Alert.alert`).
- 10 screen-level tests (empty state, populated cards with countdown, error+retry, module
  add/reorder, delete confirmation and cancellation, exam creation with UTC conversion and
  module linking, domain validation surfacing, edit prefill in local time).

### Deletion strategy (spec I, ADR-0007)

Archive is the primary, reversible retirement path (status column; data retained). Hard
delete is explicit: the confirmation lists the number of modules and exams that will be
removed, cascade is handled by FKs in one transaction, and profile data is never touched.

## Known limitations

- Migration 0002 and the authz checks have not run against a live Supabase project (the
  founder has not created one yet — see M1 worklog). They are exercised the moment the
  project and secrets exist.
- Module reordering uses per-row updates (fine at M2 scale) and ↑/↓ buttons rather than
  drag-and-drop.
- Date/time entry is text-based (`YYYY-MM-DD` / `HH:MM`) to stay dependency-free and
  identical across platforms; a native picker can replace it later without touching the
  domain layer.
- No telemetry events: no telemetry abstraction exists yet (spec L applies only "if
  present").
