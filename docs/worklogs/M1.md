# M1 — Authentication and User Shell

- **Date:** 2026-08-12
- **Status:** Complete
- **Spec basis:** Playbook v2 (§5 environment, §8 security/RLS, §19 milestones), Blueprint v2
  (auth + profile + app shell), founder's written M1 requirements

## Scope delivered

- **Supabase-class auth foundation** (`apps/app/src/lib/supabase.ts`,
  `apps/app/src/features/auth/`): lazy singleton Supabase client, email/password sign-up,
  sign-in, sign-out, session restoration on launch, auth-state listener, and automatic token
  refresh tied to the app's foreground state. The client uses AsyncStorage for session
  persistence on iOS/Android and localStorage on web. When Supabase environment variables are
  absent the app still builds and runs; auth reports a `backend-unavailable` state with a
  user-safe message instead of crashing.
- **Route protection** (`apps/app/app/_layout.tsx`, `src/features/auth/guards.ts`): expo-router
  file-based navigation with `(auth)` and `(app)` groups. A pure `decideRoute(status, group)`
  function drives redirects: signed-out (or backend-unavailable) users are always sent to
  sign-in; signed-in users are kept out of the auth screens; a full-screen loading state shows
  while the stored session is being restored, so protected content never flashes.
- **User-safe errors** (`src/features/auth/errors.ts`): every provider error is mapped to one of
  a small set of friendly messages (invalid credentials, duplicate account, weak password,
  invalid email, expired session, network failure, backend unavailable, unknown). Raw provider
  error text is never rendered.
- **Minimal user profile** (`src/features/profile/profileApi.ts`,
  `supabase/migrations/0001_user_profiles.sql`): `public.profiles` — user id (references
  `auth.users`), email, role (default `student`), timezone, program type
  (`absn | bsn | adn | other`), created/updated timestamps. A security-definer trigger creates
  the profile row automatically on sign-up. No health-related information is collected. The
  table is named `profiles` (not `users`) to avoid shadowing `auth.users`.
- **Row-level security** (migration 0001): RLS enabled **and forced**; a user can select only
  their own row and update only their own row; Postgres **column-level grants** restrict updates
  to `timezone` and `program_type` — role and email changes are rejected by the database itself.
  Insert/delete are not granted to clients at all. The client additionally sanitizes update
  payloads (`sanitizeProfileUpdate`), but the database is the authority.
- **Authorization test harness** (`scripts/authz-check.mjs`, `pnpm run test:authz`): a
  server-side script that creates two throwaway users against a real Supabase project and
  verifies nine authorization properties (own-row read, cross-user read blocked, unscoped select
  scoped to self, allowed-field update works, role/email updates fail, cross-user update is a
  no-op, insert/delete blocked, anonymous client reads nothing). It exits `SKIPPED` (code 0)
  when project secrets are not configured, so it can run unconditionally in CI and activates
  once secrets exist. The service-role key it needs is server-side only and never appears in the
  app bundle.
- **Authenticated shell** (`src/ui/`, `app/(app)/`): six destinations — Home, Courses, Study,
  Weaknesses, Progress, Profile. Courses, Study, Weaknesses, and Progress are clearly labeled
  "Not yet available" placeholders naming their future milestone. Profile is functional: shows
  email and member-since, lets the user edit timezone and program type, and signs out.
- **Responsive navigation** (`src/ui/ResponsiveShell.tsx`, `navLayout.ts`): bottom tab bar below
  768 px, persistent sidebar at ≥768 px. Layout choice is a pure function of window width; the
  destination list and all business logic are shared — nothing is duplicated per form factor.
- **Environment config** (`packages/config/src/env.ts`, `.env.example`):
  `EXPO_PUBLIC_SUPABASE_URL` and `EXPO_PUBLIC_SUPABASE_ANON_KEY` added as optional,
  schema-validated variables. These are public by design (see ADR-0006).
  `SUPABASE_SERVICE_ROLE_KEY` is documented as strictly server-side.

## Testing performed

- 41 automated tests across 7 suites (all passing): error mapping (including a raw-message leak
  check), route-guard decisions for every status/group combination, AuthProvider lifecycle with
  a controllable fake client (session restoration, sign-in/out transitions, listener
  unsubscribe), profile API ownership scoping and privilege-escalation stripping, responsive
  layout breakpoints, env schema (including malformed Supabase URL rejection).
- Full validation suite green: lint, format check, typecheck, tests, web export.
- Manual verification: exported web build served locally; index and JS bundle return 200 and the
  bundle contains the sign-in, sign-up, and shell content. Live end-to-end auth against a real
  Supabase project could not be run because no project exists yet (see limitations).

## Known limitations

- No live Supabase project yet, so live sign-up/sign-in/RLS verification is pending founder
  setup (`supabase/README.md` has the steps); `test:authz` currently reports SKIPPED.
- Email-confirmation behavior on sign-up depends on the Supabase project setting; the sign-up
  screen already handles the "check your email" case.
- Password reset and Apple/Google sign-in are structurally accommodated (error kinds, screens,
  provider abstraction) but intentionally not implemented in M1.
