# Ask Avidia latency — known limitation

Ask Avidia tutor replies are generated by the same background worker that
processes document ingestion (`apps/worker/src/learningGeneration.ts`,
invoked from `apps/worker/src/index.ts`). In production that worker only
runs as a scheduled GitHub Actions job (`.github/workflows/worker.yml`) —
GitHub Actions runners are ephemeral, so there is no always-on process today.

As of this fix the schedule runs every 5 minutes (tightened from 15 minutes),
and the app UI (`AskAvidiaScreen.tsx`) polls automatically for up to 90
seconds after a message is sent, so most replies now appear without any
manual action. But the schedule is still the ceiling: in the worst case a
student can wait up to ~5 minutes for a reply, which is not truly
interactive chat latency.

## Why this fix stopped short of a low-latency path

The three simplest "seconds, not minutes" options were considered:

- **A continuously running worker process** — would need an always-on host
  (a small VPS, Fly.io/Render worker, etc.). That is new infrastructure and
  a new account/credential the founder would need to provision; out of
  scope for a bug fix.
- **A server/API endpoint invoked directly by the client** — the web build
  (`apps/app`) deploys as a static site to GitHub Pages
  (`.github/workflows/deploy-web.yml`), which cannot execute server-side
  code. This option isn't available without changing the hosting model.
- **A Supabase Edge Function** invoked synchronously by the client right
  after the message is inserted — the best fit for the existing stack (the
  client already talks to Supabase directly, and the function can use the
  project's service-role key the same way the worker does), but deploying
  and securing it needs the Supabase CLI/project link and the Edge
  Function's own copies of `OPENAI_API_KEY` set as Supabase project
  secrets — steps only the project owner can safely perform, and not
  something verifiable end-to-end without live deploy access.

## Recommended next step

Add a Supabase Edge Function (e.g. `supabase/functions/tutor-respond`) that
performs the same retrieval + AI-router + insert steps as the `tutor` branch
of `processLearningRequest()` for a single message, and have
`sendTutorMessage()` invoke it directly instead of relying solely on the
queue. Keep `case_study` and `simulation` generation on the existing async
worker queue — those are expected to take longer and don't need sub-minute
latency.
