# M13 — Intelligent Study Planner, Calendar, Exam Countdown, and Notifications

Date: 2026-08-14. Builds on M12 (`d444bc8`).

Scope note: M13 moves Avidia from "what should I study right now?" to
"what should I study between now and my exam?". The instruction's core
principle shaped everything: M13 IS NOT ANOTHER MASTERY ENGINE. M8 stays
the sole authority for mastery, review urgency, priority, and spaced
repetition; M12 for analytics and readiness. The planner CONSUMES their
outputs and answers only WHEN the student should study WHAT — pure,
deterministic, LLM-free.

## What shipped

### Planner architecture (spec A/N — ADR-0034)

`packages/planner` is a new pure package: `createStudyPlan(input) →
StudyPlanResult`, plus `getTodayPlan`, `getUpcomingPlan`, availability
helpers, reminder builder, and session-to-activity matching. The UI never
computes schedules — it fetches stored rows and renders. All rules are
stamped `PLANNER_RULES_VERSION = 1`; every constant (slot minutes,
diversity caps, urgency weights, evidence thresholds) lives in one
documented `config.ts`.

### Availability model (spec B/C)

Per-weekday minutes (0–240) with presets LIGHT ~20, STANDARD ~45,
INTENSIVE ~90, and CUSTOM per-day values. Presets are plain descriptions
of time, never learning-quality judgments; the settings copy says so.
Stored in `planner_settings` (one row per user, defaults on first read).

### Daily study budget (spec D/P/Q)

Each plan day carries `availableMinutes` vs `plannedMinutes`; placement
never exceeds the day's budget. When total need exceeds horizon capacity
the plan sets `overCapacity` and the UI states the constraint honestly,
then triages in the fixed order: misconception remediation → exam
priorities → due reviews → unassessed coverage → higher-order practice →
enrichment. Nothing is silently compressed or dropped without the flag.

### Plan-generation algorithm (spec E/N/O)

Three phases. **Demand** (`demand.ts`): each course emits typed
`DemandItem`s from existing engine outputs — M8 `rankConcepts` snapshots
(priority practice), M8 due-review IDs (review blocks, ~3 min/concept,
5–15 min blocks), misconception signals (10-min slots, max 2/course —
spec J diversity), unassessed concepts (10-min coverage blocks, max 3 —
spec I, gathering evidence, never calling unassessed weak), M12
cognitive-level accuracy < 60% on application/analysis (Priority
Challenge via M10 — spec K), simulation availability (one 20-min
simulation per plan per course, only with ≥25% coverage, an eligible
case, and questions — spec L), and keep-fresh enrichment when nothing is
urgent (spec H/AR case H). Every item carries deterministic reason codes
(`exam_soon`, `low_mastery`, `review_due`, `misconception_signal`,
`coverage_gap`, `higher_order_gap`, `clinical_practice`, `keep_fresh`)
with exam countdowns where relevant (spec O). **Triage:** items sort by
the tier order above. **Placement:** items fill days front-to-back within
budgets over a 14-day horizon (capped at the last exam window when
sooner).

### Multi-exam and cross-course strategy (spec F/G)

Per-course weights = base 1 + urgency (closer exam → up to +2) + a +0.5
coverage boost when substantial scope is unassessed, then `splitBudget`
distributes each day's minutes proportionally. A 3-day exam gets more
time than a 10-day exam, but a farther exam with big unmet coverage is
never starved (golden case C asserts both courses receive time). The
schedule is student-level; every activity row remains course-scoped —
concept/mastery data never mixes between courses.

### Due reviews, coverage, misconceptions, clinical judgment, simulations

- Due reviews are RESERVED (tier 3) — an exam never postpones all spaced
  repetition (spec H; case D asserts review allocation with strong
  mastery).
- Coverage blocks are diagnostic, reasoned `coverage_gap` (case E).
- Misconception slots cap at 2/course/plan — no all-day hammering.
- Higher-order gaps schedule the existing M10 Priority Challenge, never a
  new drill type; only modes actually eligible (M10 `modeAvailability`)
  are planned (spec M).
- Simulations appear only when a case exists, time allows, and coverage
  suggests foundations are in place.

### Recalculation, missed days, extra study (spec R/S/T)

Recalculation IS regeneration: any trigger (completion, missed day, exam
change, availability change) rebuilds the plan from CURRENT evidence and
saves a new revision. Missed Tuesday work is re-triaged across remaining
days — never stacked onto Wednesday (case F: no day exceeds its budget
after missing two days). Extra completed study raises mastery/attempt
counts in the inputs, so satisfied work simply stops being demanded
(case G). Copy is supportive; there is no guilt messaging anywhere.

### Completion states (spec U/Z/AN)

`planned → started → completed / skipped`, plus `superseded` (replaced by
a newer revision while pending) and `expired`. Completion is
EVIDENCE-BASED: `complete_planned_activity` requires a caller-owned,
same-course, status-completed study session or simulation session;
partial sessions still count as real learning and reduce future demand at
the next regeneration. Screen-opens complete nothing. Idempotency:
re-completing is a no-op; per-column unique indexes stop one session from
satisfying two activities (double-spend tested in authz section 61).
`matchSessionsToActivities` (pure) reconciles actual sessions to pending
activities on load.

### Persistence and versioning (spec AL/AM — migration 0014)

`planner_settings`, `study_plans` (revision, horizon, timezone,
rules_version, totals, `over_capacity`; a partial unique index enforces
one ACTIVE plan per user), and `planned_activities` (date, position,
type, concept, mode, minutes, reasons jsonb, status, session refs).
Writes go only through SECURITY DEFINER RPCs (`save_study_plan`,
`start/complete/skip_planned_activity`); `save_study_plan` validates
every course belongs to the caller and supersedes only pending rows of
the old revision — completed/skipped history is never mutated (authz
section 62 verifies). No M9 session data is duplicated; activities point
at sessions.

### Today view, week view, exam countdown (spec V/W/X/Y/AV/AW)

`/planner` leads with exam countdown badges (existing `examCountdown`,
student timezone, today/tomorrow/N-days/completed handled), then Today's
activities with per-item Start/Skip and the primary CTA START TODAY'S
PLAN, which starts the first pending activity and routes into the
EXISTING M9 adaptive session, M10 mode, or M11 simulation
(`activityLaunchRoute`) — no duplicated study engines (spec Y). Below:
a simple upcoming-days list (spec W — deliberately not a calendar grid).
The Today home screen gained a "Your study plan" card linking to the
planner. Desktop uses the existing ResponsiveShell; no separate app.

### Notifications (spec AA–AI — ADR-0035)

LOCAL notifications only — no push infrastructure, no device tokens
(spec AH decision documented in ADR-0035). The pure engine's
`buildReminderInstructions` decides content and timing: per-type opt-in
prefs (ALL DEFAULT OFF — spec AE), reminder hour in the student's
timezone, quiet hours deferring to window end (spec AD), volume caps
(one study reminder per planned day, one review reminder per due day,
exam reminders at 3 and 1 days — spec AA), and privacy-conscious bodies
carrying only minutes and countdowns, never performance (spec AF/AP).
Permission is requested ONLY when a student flips a toggle in settings
(spec AB); denial and `canAskAgain=false` are respected without nagging.
Sync is cancel-then-reschedule keyed by stable IDs, so replans never
stack duplicates and superseded plans can't fire stale reminders.
Notification taps route through `safeDeepLink` (allowlist `/planner`,
`/home`, `/study`; anything else → `/home` — spec AG). Web:
`expo-notifications` is lazily imported and never touched; the settings
screen explains reminders are app-only and the planner works fully
without them (spec AI).

### Timezone strategy (spec AJ)

Canonical timestamps are UTC; study days, exam countdowns, reminder
times, and quiet hours resolve in the student's profile timezone via the
same domain helpers as M9–M12. `localDateKey`/date tests cover DST
spring-forward and fall-back, midnight boundaries, and exam-day/tomorrow
transitions. Nothing hard-codes Central Time.

### Security and privacy (spec AO/AP)

RLS on all three tables (settings direct-own; plans/activities
select-own/through-plan; all writes RPC-only with auth.uid() checks).
`scripts/authz-check.mjs` sections 59–62 add ~25 checks: User B cannot
read or spoof User A's settings, plans, or activities (guessed IDs);
invalid presets/hours rejected; save validates course ownership;
completion demands owned evidence; double-spend blocked; revisioning
preserves history; cascade cleanup leaves no orphaned activities.
Notification payloads never leave the device.

### AI independence and empty states (spec AQ/AR/AS)

No LLM anywhere in generation, recalculation, countdown, or reminders —
the planner works with every AI provider down. Empty states: no courses →
gentle onboarding CTA; zero availability → prompt to set time; no exam →
general review/keep-fresh plan (case H); no mastery data → coverage
blocks; no due reviews → time flows elsewhere; no eligible simulation →
none scheduled. New users configure nothing up front: standard preset
defaults let "Build my plan" work immediately.

### Analytics connection (spec AT)

Plans and activities are clean structured rows (dates, statuses,
minutes, reasons) that M12+ can aggregate later ("4 of 5 planned days
completed") without schema changes. M12 itself was not redesigned.

### Accessibility (spec AU)

Every interactive element has `accessibilityRole`/`accessibilityLabel`
(preset chips include selected state; day chips announce minutes; hour
steppers announce direction), touch targets are ≥44pt, statuses use text
("✓", "skipped") not color alone, and copy stays plain-language.

## Testing

- `packages/planner`: 46 tests — availability/clamping, date/DST
  handling, demand construction, golden cases A–H (distribution, triage
  under 30 min, two-exam split, review reservation, coverage allocation,
  missed-day recalculation without overload, extra-study absorption,
  no-exam plan), budget splitting, reminder prefs/quiet hours/caps/
  privacy, and session→activity matching (idempotency, type
  compatibility, course scoping).
- App: `launch.test.ts` (labels cover all 9 types and 8 reason codes,
  countdown copy, launch routes, deep-link allowlist) and
  `planner.test.tsx` (empty states, Today render with countdown +
  reasons, START TODAY'S PLAN start+route, skip, completed-day state,
  over-capacity constraint) — 19 tests.
- `scripts/authz-check.mjs` sections 59–62 (RLS, spoofing, evidence,
  double-spend, revisioning) run against a live Supabase instance.

## Limitations

- Reminders schedule only when the app builds/refreshes a plan (no
  background scheduler); acceptable for local-notification scope.
- The authz suite still requires live Supabase env vars to execute
  (skips cleanly otherwise); the Supabase project itself remains to be
  provisioned by the owner.
- Week view intentionally minimal (list, not calendar grid) per spec W.
- No external calendar sync (spec AK) — internal planner only.

## M14 handoff

M13 is complete and validated. Not started (per instruction): whatever
M14 defines. Natural candidates the data now supports: plan-adherence
analytics surfaced in M12 screens (spec AT), push notifications if
server-initiated messaging ever becomes a requirement, and richer
availability (e.g., per-date exceptions). No architectural blockers are
known; the planner's revisioned rows and pure engine are designed to be
consumed as-is.
