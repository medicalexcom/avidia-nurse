# M6 — Nursing concept and knowledge model

Date: 2026-08-13. Builds on M5 (`4b59f83`).

Scope note: this milestone ships the structured knowledge layer — concept
extraction, normalization, provenance, relationships and a restrained
student view. It is explicitly NOT the adaptive study interface, and there
are no quizzes, mastery tracking, spaced repetition, difficulty modeling,
exam prediction or content generation (spec V). Study tooling that
_consumes_ this model is M7+.

## What shipped

- **Migration `0006_concepts_and_knowledge.sql`** — `concepts`,
  `concept_aliases`, `concept_sources`, `concept_relationships` (all
  course-scoped, forced RLS, owner-read-only, client-write-denied), the
  `knowledge_status` lifecycle on `documents` (pending → extracting →
  ready | failed, independent of M4/M5 states), two SECURITY DEFINER
  worker-only RPCs — `apply_concept_extraction` (transactional, idempotent
  apply with dedup/alias resolution/orphan prune) and
  `recompute_concept_emphasis` — plus an `AFTER DELETE` trigger on
  `documents` that prunes AI concepts left without evidence.
- **`@avidia/knowledge` package** — deterministic normalization
  (ADR-0015), strict extraction schema + validator, the
  provider-independent extraction gateway (OpenAI `gpt-4o-mini` strict
  JSON-schema mode + scripted offline provider, ADR-0016), refinement
  (dedup, alias merge, fullest-name promotion, type coercion, relationship
  filtering), the SHA-256 fingerprint cost gate, chunk batching, and the
  synthetic nursing eval fixtures (spec U).
- **Worker knowledge stage** — indexed documents flow through
  claim → fingerprint check → batched extraction → refine → RPC apply →
  ready, with stale-claim recovery, failure isolation (a failed extraction
  never touches processing/index status — the document stays fully
  retrievable, spec T) and honest logs including "knowledge unchanged
  (fingerprint match, no AI call)".
- **Domain** — `CONCEPT_TYPES` / `CONCEPT_RELATIONSHIP_TYPES` with student
  labels, `KnowledgeStatus`.
- **App** — Concepts list (emphasis-ordered, typed, "found in N places in
  your materials") and concept detail with aliases, evidence grouped by
  document with human locators ("Module 2 Electrolytes.pdf — slide 18;
  slide 21") and material-supported relationships rendered as sentences
  ("Furosemide may cause Hypokalemia"). Guessed/foreign ids render exactly
  like not-found (spec R).
- **Authz harness** — M6 checks 28–33: RPC denial, owner reads with
  evidence, cross-user/anon guessed-id denial on all four tables, direct
  client write denial, document-delete orphan prune, course-delete cascade
  including all concept tables.

## Key decisions (ADRs 0014–0017)

- **Course-scoped, never global** (ADR-0014) — a deliberate deviation from
  Playbook §7's shared ontology; private material can never leak between
  users or courses at the schema level.
- **Deterministic-first dedup** (ADR-0015) — formatting-only normalized
  keys make hyperkalemia/hypokalemia false merges structurally impossible;
  aliases are first-class with fullest-name promotion (DKA → Diabetic
  Ketoacidosis).
- **Strict AI extraction** (ADR-0016) — schema-constrained `gpt-4o-mini`
  at temperature 0, one controlled repair round, full version/audit trail,
  fingerprint gate so unchanged content never re-bills.
- **Evidence-bound relationships** (ADR-0017) — every edge carries a chunk
  FK that cascades; no generic medical knowledge graph.

## The emphasis decision (spec L)

Implemented as a transparent evidence count: `emphasis_score` = number of
supporting source links, recomputed server-side after every apply. The UI
words it as "found in N places in your materials" — a study-priority
signal derived from how much of the student's own course covers the
concept. It is never presented as an exam prediction, importance ranking by
the AI, or clinical priority.

## Quality evaluation (spec U)

`EVAL_EXTRACTION_CHUNKS` + `EVAL_EXPECTED_CONCEPT_KEYS` in
`@avidia/knowledge` form a synthetic nursing fixture set (electrolytes,
DKA, meds, junk headers). The refine test suite proves, repeatably: all 9
expected concepts found; junk ("Chapter Overview", "Blood", "Patient")
dropped with telemetry; DKA merged with its expansion, alias kept, chunk
provenance intact; near-twins kept separate; unknown types coerced to
`other`; exactly 4 relationships with chunk evidence; byte-identical output
across repeated runs. Re-run any time with `pnpm test` — no API key needed
(scripted provider).

### Manual validation steps (spec Y — run once Supabase project exists)

1. Apply migration 0006; confirm all four concept tables exist with RLS
   forced and no client grants beyond SELECT.
2. Sign in as a student, upload a PPTX with a slide on hyperkalemia; watch
   `documents.knowledge_status` go pending → extracting → ready.
3. Open Course → Concepts; confirm concepts appear ordered by emphasis
   with type labels and "found in N places".
4. Open a concept; confirm evidence lists the real document name and slide
   numbers that actually contain the concept.
5. Upload a second document mentioning the same concept differently (e.g.
   "high K+"); confirm ONE concept with the alias recorded, emphasis
   increased, both documents in evidence.
6. Upload a document with "DKA" where another says "Diabetic
   Ketoacidosis"; confirm the canonical name is the full form and DKA is
   an alias.
7. Confirm hyperkalemia and hypokalemia remain two distinct concepts.
8. Re-run the worker with no content changes; logs must show the
   fingerprint skip and provider must receive zero requests.
9. Edit/replace a document's file; confirm re-extraction runs and evidence
   for the old content disappears (no stale links, spec O).
10. Delete a document whose concepts have no other source; confirm those
    AI concepts are pruned and shared concepts survive with reduced
    emphasis.
11. Delete the course; confirm all four concept tables have zero rows for
    it.
12. As user B, request user A's concept id directly (API and app URL);
    confirm empty result and a not-found screen identical to a nonsense
    id.
13. Attempt client-side `apply_concept_extraction` /
    `recompute_concept_emphasis` and direct concept-table writes; all
    denied.
14. Kill the worker mid-extraction; confirm the stale sweep returns the
    document to pending and a retry produces no duplicate concepts.
15. Set an invalid `OPENAI_API_KEY`; confirm extraction fails fast, the
    document shows knowledge failed WITH detail, and search/retrieval over
    the document still works (spec T).

## Known limitations

- Merging depends on deterministic keys + extracted aliases; synonyms with
  no lexical overlap stay separate concepts until curation exists.
- `emphasis_score` counts evidence links; it does not weight document
  types or recency.
- Relationship extraction is conservative (evidence-bound, controlled
  types); sparse materials yield sparse graphs by design.
- The quality eval measures the deterministic pipeline; live-model quality
  against the fixtures needs an API key and is a manual run for now.

## Handoff to M7

The knowledge model is ready to be consumed: course-scoped concepts with
types, aliases, evidence, relationships and transparent emphasis. M7 (item
engine) can build study items on top of `concepts`/`concept_sources`
without touching extraction. Not started here per instruction.
