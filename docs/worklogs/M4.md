# M4 — Document Extraction and Processing

## Scope delivered

M4 turns stored course materials (PDF, PPTX, DOCX, TXT) into ordered,
provenance-preserving `document_sections` rows via a background worker, with a
strict processing state machine, idempotent reprocessing, and student-safe
error reporting. No AI/LLM calls anywhere; deterministic parsers only
(spec A, Q).

### Extraction architecture (spec A; ADR-0009)

A new workspace package, `packages/ingestion`, owns all parsing. Its single
entry point is:

```ts
extractDocument(bytes: Uint8Array, extension: MaterialExtension): Promise<ExtractionResult>
```

It is pure computation — no network, no database, no React — so it is fully
unit-testable and reusable by any future runtime (worker, edge function,
batch backfill). Failures throw `ExtractionFailedError` with a specific code
(`no_text`, `ocr_required`, `encrypted`, `malformed`, `unsupported`) plus an
internal-only detail string.

### Parser choices (ADR-0009)

- **PDF:** `pdfjs-dist` (Mozilla's PDF.js, legacy CJS build, pinned to
  3.11.174) — mature, pure-JS, battle-tested; gives per-page text with
  end-of-line markers and distinguishes password-protected files.
- **PPTX / DOCX:** `jszip` + `fast-xml-parser` (preserveOrder mode) with a
  small OOXML helper layer. Only `a:t` / `w:t` text nodes become content, so
  no XML garbage, drawing coordinates, or theme metadata can leak into
  sections (spec C).
- **TXT:** hand-rolled normalization (BOM strip, newline unification,
  control-character removal, whitespace collapse) with deliberately
  conservative heading detection — a single short line that is markdown-`#`
  or ALL CAPS; nothing else is promoted, so structure is never invented
  (spec E).

### Normalized content model (spec F; migration `0004`)

`document_sections`: `id`, `document_id` (FK → documents, ON DELETE CASCADE),
`section_type` (`heading` | `paragraph` | `list` | `table` | `slide_title` |
`slide_body` | `slide_notes` | `page_text`), `sequence` (gapless, 0-based,
unique per document), `page_number`, `slide_number`, `heading` (nearest
enclosing heading/slide title), `content` (1–20 000 chars), `metadata` JSONB
(e.g. table `rows`/`columns`, heading `level`, list `items`), `created_at`.
This is a queryable relational model, not an opaque JSON blob.

### Provenance (spec B, C, G)

- PDF: one `page_text` section per page with `page_number`; pages are never
  flattened into one string. Oversized pages split at line boundaries without
  losing order.
- PPTX: slide order comes from `p:sldIdLst` joined to the presentation rels —
  the authoritative order, not file names. Every section carries
  `slide_number`; bodies/tables/notes carry the slide title as `heading`.
  Slide-number/footer/date placeholders are excluded as chrome.
- DOCX: body walked in document order; paragraphs and tables carry the
  nearest preceding heading; consecutive numbered/bulleted paragraphs merge
  into one `list` section with indentation by `w:ilvl`.
- `describeSectionSource()` (domain) renders provenance like
  "slide 21" / "page 4" / "section “Postoperative Complications”" for M5+.

### Processing state machine (spec H; ADR-0010)

`UPLOADED → QUEUED → PROCESSING → READY | FAILED`, enforced by a database
trigger (`enforce_document_status_transition`) that rejects illegal
transitions AND reserves entry into `processing`/`ready` for the service role
(`auth.uid()` is null). Clients can enqueue (`uploaded → queued`,
`failed → queued`) but can never fake a READY document. `error_message` holds
only student-safe text; internal diagnostics go to `processing_detail`, which
is not in the authenticated column grant. `processed_at` and
`processing_attempts` complete the audit trail.

### Background processing design (spec J, O)

`apps/worker` is a standalone Node process (`tsx`), run as
`pnpm --filter @avidia/worker start` (poll loop, 5 s) or `start:once` (drain
and exit). All I/O goes through the `WorkerClient` interface
(claim/download/replaceSections/markReady/markFailed/recoverStaleProcessing),
so the current Postgres-as-queue polling can later be swapped for a durable
queue without touching extraction or state logic. Extraction is nowhere near
a React component. Claiming uses an optimistic compare-and-set
(`UPDATE … WHERE processing_status = 'queued'`), so concurrent workers never
double-process. A sweep fails documents stuck in `processing` for >15 min so
students can retry after a worker crash.

### Idempotency and retry (spec I)

All section writes go through one SECURITY DEFINER RPC,
`replace_document_sections(document_id, sections)`, which deletes and inserts
atomically in a single transaction. Reprocessing therefore converges to the
same rows — duplicates are impossible by construction, and a retried document
(`failed → queued`) is rebuilt from scratch.

### Tables (spec M)

PPTX (`a:tbl`) and DOCX (`w:tbl`) tables become `table` sections with
pipe-separated rows (`Test | Range`) and `metadata: { rows, columns }` — lab
values and medication tables stay readable and machine-recoverable.

### OCR decision (spec L)

No OCR is performed. A PDF whose pages yield fewer than 25 extractable
characters in total is failed with code `ocr_required` and the message "no
selectable text — looks like scanned images; text recognition (OCR) is not
yet available". The Playbook does not assign OCR to M4, so it is deferred,
and the state is explicit rather than a silent empty READY.

### Failure handling (spec N)

Zero sections, contract violations (`validateSectionBatch`: gapless
sequence, known types, non-empty bounded content), encrypted files, corrupt
archives and truncated files all map to specific failure codes and land the
document in FAILED with a clean student message. A document can never reach
READY with empty or broken content — the quality gate runs before any write.

### Security (spec O)

The worker uses `SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY` (server-side env
only, never `EXPO_PUBLIC_*`, never bundled). `document_sections` has forced
RLS with a SELECT-only policy through course ownership; clients cannot
insert/update/delete sections or call the replace RPC (revoked). The worker
logs document ids, statuses and counts only — never file content, storage
keys, tokens or credentials. It processes only rows that exist in the
`documents` table, which the state machine and RLS already constrain.

### UI (spec K)

The Materials screen now distinguishes states meaningfully: Queued /
Processing / Ready; a failed _upload_ (no stored object) still offers "Try
again" (re-pick), while a failed _processing_ run (object safely stored)
shows "Processing failed" with the student-safe reason and a
"Try processing again" action that just re-enqueues. Uploads auto-enqueue on
success (best-effort — if enqueueing fails the document rests at Uploaded
with a "Process" button). No stack traces, parser internals or file paths
appear anywhere in the UI.

### Fixtures (spec S)

`packages/ingestion/src/fixtures.ts` builds deterministic, legally safe
files in memory (a handcrafted minimal PDF; JSZip-built PPTX/DOCX) from
known fictional nursing content — no binaries in the repository, no
copyrighted educational material.

### Tests (spec T)

- Domain: section-source description + section-batch validation (3 new).
- Ingestion (10): PDF multi-page provenance/ordering, image-only →
  `ocr_required`, malformed; PPTX titles/bullet hierarchy/tables/notes/slide
  order/chrome exclusion; DOCX headings/paragraphs/lists/tables/order; TXT
  normalization/conservative headings/empty file.
- Worker (8): queued→processing→ready with stored sections; empty queue;
  scanned-PDF failure with safe message and separated internal detail;
  corrupt-file failure + retry to ready; idempotent replacement; missing
  storage_key defensive failure; queue draining; stale-processing recovery.
- App (70): existing flows plus Process/enqueue, processing-failure retry
  without re-upload, and Ready-state rendering.
- Authz harness (runs against a live project): owner can enqueue; clients
  cannot enter processing/ready; only the service role can write sections;
  cross-user/anonymous section reads return nothing; course deletion
  cascades to sections (spec U).

## Known limitations

- No live Supabase project yet (founder setup pending), so the authz harness
  and the 17 manual verification steps remain to be executed once the
  project exists and migrations 0001–0004 are applied.
- The queue is Postgres polling, not a durable message queue; the
  `WorkerClient` seam is the designed migration path.
- No OCR (documented above); image-only PDFs fail with a clear state.
- pdfjs-dist is pinned to 3.11.174 (last CJS-compatible legacy build for the
  Jest toolchain); upgrading to v4+ requires an ESM test setup.
- The worker must be run and hosted manually (`start` / `start:once`); no
  deployment target is defined yet.

## M5 handoff (spec R)

Every extracted unit answers: DOCUMENT (`document_id`) → STRUCTURAL UNIT
(`section_type`) → ORDER (`sequence`) → CONTENT (`content`) → SOURCE LOCATION
(`page_number` / `slide_number` / `heading`). M5 (Concepts/RAG per Playbook
§19: ontology seed, embeddings, pgvector `source_chunks`, concept map,
retrieval) will _derive_ its semantic chunks from `document_sections`;
nothing in M4 creates embeddings or retrieval structures (ADR-0010).
