# M14 — Subscription System, Entitlements, Production Hardening, and Release Infrastructure

Date: 2026-08-14. Builds on M13 (`1d5f42e`).

Scope note: two principles governed every decision. **Payments are never
client-authoritative** — the only writer of subscription state is a
signature-verified webhook, and every FREE-plan limit is enforced by
database triggers that ignore what the client claims. **Learning data
never disappears when a subscription expires** — expiry changes what can
be CREATED going forward, never what already exists. M14 adds a
monetization and hardening layer AROUND the stable M0–M13 learning
systems; none of them were redesigned.

## What shipped

### Entitlement model (spec A/B/L — ADR-0037)

`packages/entitlements` is a new pure package (25 tests). Two plans only:
`free` and `pro`. Features ask `canUser(payload, 'advanced_modes')` —
never `plan === 'pro'` — and the plan → capability mapping lives in ONE
place (`PLAN_DEFINITIONS`, `ENTITLEMENTS_RULES_VERSION = 1`, mirrored by
the SQL `get_my_entitlements()`). FREE keeps the core loop genuinely
useful: course uploads, adaptive study, patient simulation, and
analytics, limited to 1 active course and monthly caps of 10 documents /
30 AI generations / 3 simulations. PRO adds `advanced_modes`,
`study_planner`, and unlimited usage. **All numeric limits are
engineering placeholders pending founder pricing approval** (the
Blueprint pricing table is labeled hypotheses).

### Subscription persistence (spec C/D)

Migration `0015_subscriptions_and_entitlements.sql` adds:

- `subscriptions` — provider (`stripe|apple|google`), provider ids,
  one of five normalized statuses (`active | trialing | past_due |
canceled | expired`), period end, `cancel_at_period_end`. Students can
  SELECT their own row; **no authenticated INSERT/UPDATE/DELETE policies
  exist at all** (authz sections 64–66).
- `billing_events` — `(provider, provider_event_id)` unique index for
  idempotency; zero client access.
- `usage_counters` — per user/resource/month; select-own only; written
  exclusively by SECURITY DEFINER functions.
- `rate_limit_hits` + `check_rate_limit()` — sliding-window limits on
  the two costly pipelines only (document upload 30/hr, simulation start
  20/hr), per spec Y/Z.
- `current_plan()` / `get_my_entitlements()` — SECURITY DEFINER; the
  single server-side authority the client reads.

### Stripe web billing (spec E/F/G/R/T — ADR-0036)

Four Supabase Edge Functions in `supabase/functions/` (Deno,
dependency-free, mirroring the unit-tested pure package):

- `stripe-webhook` — verifies Stripe's HMAC-SHA256 signature over
  `${t}.${body}` with constant-time comparison and 300s replay
  tolerance; deployed `--no-verify-jwt` (the signature IS the
  authentication). It is the ONLY writer of `subscriptions`. Duplicate
  event ids are acknowledged 200 and processed zero times (case AY-D);
  unattributable subscription events return 500 so Stripe retries after
  the linking `checkout.session.completed` arrives.
- `create-checkout-session` / `create-billing-portal-session` —
  authenticated; return Stripe-hosted URLs only. No custom card UI
  exists anywhere; card data never touches Avidia (spec T). When Stripe
  isn't configured they return an honest 503 `billing_not_configured`.
- `health` — dependency probe returning status + database latency
  (spec AI).

### Store billing abstraction (spec H/I/J/Q — ADR-0038)

`StorePurchasesAdapter` (`isConfigured/purchasePro/restorePurchases`,
closed outcome unions) is the single integration boundary. The app ships
the documented `notConfiguredPurchases` stub: on native, checkout and
Restore Purchases report honestly that purchases aren't available in
this build yet. **No product IDs were fabricated and store billing is
not claimed production-complete** (spec I). The adapter contract's key
rule: a store purchase NEVER grants access locally — the store backend's
webhooks write the same normalized `subscriptions` rows, and
`normalizeStoreState` maps store states onto the same five statuses, so
Apple/Google/Stripe are indistinguishable to the entitlement layer.

Manual activation steps (founder, when accounts exist): create Apple
Developer + Google Play accounts; define the PRO subscription product in
App Store Connect / Play Console; create a RevenueCat project with those
products and API keys; implement a RevenueCat-backed adapter and swap
the export in `apps/app/src/features/billing/purchases.ts`; point
RevenueCat webhooks at a server writer into `subscriptions`. Interface,
tests, entitlement layer, and UI paths are already in place.

### Server-authoritative enforcement, flag-gated (spec K/AE)

All FREE-limit triggers (`courses` 1-active-course, `documents`
monthly + rate limit, `simulation_sessions` monthly + rate limit) no-op
while the `subscriptions` feature flag is FALSE — the shipped default.
M0–M13 behavior and its entire test suite are unchanged until billing is
deliberately launched. **The launch switch is one row:**

```sql
update public.feature_flags set enabled = true where flag = 'subscriptions';
```

Usage counters record ALWAYS regardless of the flag (spec W/X): cost
visibility does not wait for monetization. AI generations are counted by
a trigger on `documents.question_status` (pending → generating),
attributed to the uploader — the worker was not modified. Limiting acts
at the upload gate, so any accepted document always processes fully.

### Client behavior and failure posture (spec L/M/N/AW)

`useEntitlements` fetches `get_my_entitlements()` and caches the payload.
On fetch failure the client trusts its last server payload for at most
72 hours (`shouldTrustCachedEntitlements`; future-dated caches are
rejected against clock tampering), then renders permissively. The
documented tradeoff (ADR-0037): UI failing CLOSED would lock paying
students out during an outage; failing OPEN grants nothing real because
every enforced limit lives in database triggers. A tampered client can
draw a button; the server still says no.

The paywall (`/upgrade`) is restrained: one screen, reached from the
profile, stating what PRO adds, what FREE keeps, that the subscription
renews until canceled, that the exact price is shown by Stripe before
payment, and that learning data stays regardless. Gating goes through
`canUser` only.

### Expiry, deletion, export (spec O/AK/AL)

Expiry downgrades access, never data: courses beyond the FREE limit stay
readable, mastery history stays, uploads stay. Grace mirrors provider
reality: `past_due` keeps access 7 days past period end (AY-F),
cancel-at-period-end keeps it through the paid period (AY-E), unknown
provider statuses normalize to `expired` and never grant access.

`export_my_data()` returns the student's profile, courses, document
metadata, mastery, sessions, simulations, plans, usage, and subscription
summary as JSON (Download my data in the profile). `delete_my_account()`
removes storage objects and the `auth.users` row (cascading everywhere)
— but REFUSES while an active/trialing/past_due subscription is not set
to cancel at period end, directing the student to cancel first. We never
silently keep charging a deleted user (verified end-to-end, authz 71).

### Observability without PHI (spec AF/AG/AH)

Analytics gained six payload-FREE events (`paywall_viewed`,
`checkout_started`, `billing_portal_opened`,
`restore_purchases_attempted`, `data_export_requested`,
`account_deletion_requested`) — names only, no user content (verified by
test). Edge functions log structured JSON without PII. The app is
wrapped in `AppErrorBoundary` (spec AV): a recoverable error screen that
logs name/message/component stack — never user content. `SENTRY_DSN` is
documented in `.env.example` as the future error-monitoring hook; no
fake integration was wired.

### Environments, migrations, backups (spec AA/AB/AC/AJ — ADR-0039)

One Supabase project per environment; production is created deliberately
by the founder near launch, never as a tooling side effect. Same secret
NAMES everywhere (documented in `.env.example`), different values, never
`EXPO_PUBLIC_*`. Migrations are forward-only, filename-ordered, staging
first; mistakes get a NEW migration. Supabase free tier has no backups —
production must be on a backed-up plan BEFORE launch with one restore
rehearsed on staging. Retention promises beyond reality were NOT
invented (spec AM); Privacy/Terms surfaces in the app are explicit
placeholders marked "pending legal review" (spec AN), and the profile
shows the educational disclaimer (spec AO).

### Security verification (spec AP/AZ + authz 64–71)

`scripts/authz-check.mjs` gained sections 64–71 against a live project:
forged premium denied (self and other), subscription IDOR denied,
`billing_events` unreachable and duplicate ids rejected, usage counters
client-unwritable, RPC authority (`record_usage`/`check_rate_limit` not
client-executable), `get_my_entitlements` per-user correctness, export
caller-scoped, deletion guard refuses then succeeds after
cancel-at-period-end. Webhook spoofing is covered by signature
verification with constant-time comparison; secret leakage by the
gitleaks CI job and `EXPO_PUBLIC_*` discipline.

### CI and dependency hygiene (spec AQ/AR/AS)

CI gained a `dependency-audit` job: `pnpm audit --audit-level high`
fails the build on HIGH/CRITICAL advisories. To make that gate honest,
the root `package.json` now:

- overrides `tar` to `>=7.5.21`, fixing a critical/high chain that
  reached the tree only through the dev-only
  `jest-expo → jsdom → canvas → node-pre-gyp` path;
- ignores exactly three advisories via `pnpm.auditConfig.ignoreGhsas`,
  each with a reason:
  - `GHSA-5p2g-fcmc-qvqq` and `GHSA-w3rx-r6r6-pgpr` (`image-size`): the
    registry lists patched versions as `<0.0.0` — no fix exists
    upstream; the package is used only at build time by Metro/Expo
    tooling on trusted local images, never on user-supplied input at
    runtime.
  - `GHSA-wgrm-67xf-hhpq` (`pdfjs-dist`): the advisory's documented
    mitigation is `isEvalSupported: false`, which
    `packages/ingestion/src/pdf.ts` has set since the option was
    introduced — the vulnerable path is disabled in our usage.

  These ignores are revisited whenever the audit gate fires or the
  dependencies update; nothing HIGH+ with an available fix is ignored.

The existing gitleaks secret-scan job runs on full history. A local
`pnpm audit` shows the remaining low/moderate advisories without
blocking merges.

## Manual validation checklist (spec BA — Stripe test mode, staging)

Prerequisites: a staging Supabase project with migrations 0001–0015
applied, edge functions deployed with test-mode Stripe secrets, a Stripe
test-mode webhook endpoint pointed at `stripe-webhook`, and the
`subscriptions` flag set true on staging.

1. Sign up as a fresh student; confirm plan shows FREE in the profile.
2. Upload a document, run a study session, start a simulation — the
   FREE core loop works.
3. Create a 2nd active course → blocked with the plan-limit message;
   archive course 1 → creating course 2 succeeds (1 ACTIVE course, not
   1 course ever).
4. Upload an 11th document within the month → blocked; existing 10
   remain untouched.
5. Start a 4th simulation within the month → blocked with honest copy.
6. Open Upgrade; verify `paywall_viewed` logs with no payload.
7. Continue to checkout → Stripe-hosted page; pay with test card
   `4242 4242 4242 4242`.
8. Return to the app; entitlements refresh to PRO without reinstall.
9. Verify a `subscriptions` row exists (status `active`, provider
   `stripe`) written by the webhook — not by any client call.
10. Re-send the same webhook event from the Stripe dashboard → 200,
    `duplicate: true`, no second row/side effect (AY-D).
11. As PRO: create multiple active courses, exceed the old monthly
    caps, use advanced modes and the study planner — all permitted.
12. Open Manage subscription → Stripe Billing Portal loads; change the
    payment method; no card field ever renders in-app.
13. In the portal, cancel at period end → app shows PRO retained until
    the period date (AY-E); learning features keep working.
14. In Stripe, expire the subscription (or advance the test clock) →
    plan returns to FREE; every course, document, mastery record, and
    simulation transcript is still present and readable (AY-C / spec O).
15. With >1 course from the PRO period: creating another active course
    is blocked, but all existing courses remain readable/archivable.
16. Simulate `invoice.payment_failed` → status `past_due`; access
    persists through the 7-day grace, then downgrades (AY-F).
17. Kill network / break the entitlement fetch → app keeps last known
    plan with the "offline — last known" note; set the device clock
    forward 4 days → cache no longer trusted, UI renders permissively,
    server-side limits still enforce (spec AW).
18. On a native build: Continue to checkout and Restore purchases both
    show the honest "not available in this build" message (AY-H); no
    fake store sheet appears.
19. Attempt forged premium: as an authenticated user, insert/update a
    `subscriptions` row via the API → denied by RLS (authz 64–66).
20. Post an unsigned/garbage payload to `stripe-webhook` → 400; nothing
    written (AZ webhook spoofing).
21. Download my data → JSON contains profile, courses, documents
    metadata, mastery, sessions, simulations, plans, usage,
    subscription summary — and only the caller's own rows.
22. Delete my account with an active subscription → refused with the
    cancel-first message; after cancel-at-period-end, deletion succeeds;
    sign-in no longer works and storage objects are gone (authz 71).
23. Hit `health` → 200 with database latency; stop the database (or use
    a bad URL) → 503 degraded.
24. Flip the `subscriptions` flag FALSE → limits stop enforcing, usage
    still records; flip TRUE → enforcement resumes. No deploy needed.

## Testing

- `packages/entitlements`: 25 tests — plan capabilities/limits, the five
  status normalizations (Stripe + store), paid-access windows (AY-E/F,
  unknown → expired), cache trust window incl. future-timestamp
  rejection, webhook event routing/snapshot/idempotency contract.
- App billing: 19 tests — cache trust/expiry/clear, `entitlementsAllow`
  permissive vs enforced, checkout URL / 503 / 404 / error mapping,
  not-configured stub for purchase and restore, delete-account outcome
  mapping, paywall honesty copy, payload-free `paywall_viewed`, error
  boundary catch + pass-through.
- `scripts/authz-check.mjs` sections 64–71 (live Supabase; skips cleanly
  without env).
- Full suite: 867 tests across the monorepo.

## Limitations

- FREE-plan numeric limits and PRO pricing are placeholders pending
  founder approval; changing them touches `PLAN_DEFINITIONS` + the SQL
  mirror (one rules version).
- Store billing is an honest stub until Apple/Google/RevenueCat accounts
  exist (activation steps above).
- Error monitoring is a documented hook (`SENTRY_DSN`), not a wired
  integration.
- The authz suite and the manual checklist require a provisioned
  Supabase project + Stripe test mode; the Supabase project itself
  remains to be created by the owner.
- Privacy Policy and Terms are placeholders pending legal review; no
  retention promises were invented.

## Non-goals honored (spec BB)

No app-store submission was performed, no launch was declared, and M15
was not started.
