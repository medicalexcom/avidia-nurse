# M3 — Course Material Upload and Storage

- **Date:** 2026-08-12
- **Status:** Complete
- **Spec basis:** Playbook v2 (§6 data model — `documents`, §8 security/RLS/Storage, §19
  milestones — "Signed uploads, document records, status UI"), Blueprint v2 (course-material
  grounding), founder's written M3 requirements

## Scope delivered

An authenticated student can upload course materials (PDF, PPTX, DOCX, TXT) or paste notes into
any course they own, see everything they uploaded in a Materials screen with type, size, date and
status, open a material through a short-lived signed URL, retry failed uploads, and delete
materials (database row **and** storage object). All of it is private: the storage bucket is
private, every access path is enforced by database RLS and storage policies, and another student
cannot see, list, download, upload into, replace, or delete anything that isn't theirs — even
with a forged client.

**No processing happens in M3.** Uploaded materials rest at status `uploaded`. Extraction,
parsing, OCR, embeddings, and everything AI is M4+ (see "M4 boundary" below).

### Database (`supabase/migrations/0003_documents_and_storage.sql`)

- **documents** — id, course_id → courses (cascade), uploaded_by → profiles (cascade),
  filename (sanitized, 1–160), original_filename (≤255), mime_type, file_extension
  (`pdf`/`pptx`/`docx`/`txt` only), file_size (>0, ≤ 50 MiB), storage_key, document_type
  (`lecture`/`study_guide`/`course_objectives`/`notes`/`textbook_excerpt`/`other`, default
  `other`), processing_status (state machine below), error_message (≤500), content_hash
  (SHA-256 hex, nullable), timestamps with the shared `set_updated_at` trigger.
- **Integrity checks in the database itself:**
  - `documents_storage_key_when_stored` — every row not in `uploading`/`failed` must have a
    storage key.
  - `documents_storage_key_matches_owner` — the storage key must match
    `uploaded_by/course_id/id/…`, so a row can never point at another user's storage folder.
- Indexes: `(course_id, created_at desc)` for listing, partial `(course_id, content_hash)` for
  duplicate detection, `(uploaded_by)`.
- The migration also creates the **`course-materials` storage bucket** (private,
  `file_size_limit` 52428800, `allowed_mime_types` restricted to the four supported types) and
  its storage policies — no dashboard clicking required beyond applying the migration.

### Row-level security and storage policies (spec C, D, K)

- `documents`: RLS enabled **and forced**. Every policy requires the parent course to belong to
  the caller (`exists` on courses with `user_id = auth.uid()`); INSERT additionally requires
  `uploaded_by = auth.uid()` — you cannot upload "as" someone else or into a course you don't
  own, even by forging the course id.
- Column-level grants: clients can INSERT only the intake columns and UPDATE only
  `storage_key`, `processing_status`, `error_message`, `document_type`. Reparenting
  (`course_id`, `uploaded_by`) is impossible.
- `storage.objects` policies for the bucket use the object path itself:
  `(storage.foldername(name))[1]` must equal the caller's uid for SELECT/DELETE, and INSERT
  additionally requires path segment 2 to be a course the caller owns. **There is no UPDATE
  policy** — objects are immutable; nobody (including the owner) can replace an object in
  place, which also blocks the "overwrite someone's file via upsert" attack.
- Authorization is by policy, never by obscurity: knowing (or guessing) another user's storage
  path gains nothing.
- `scripts/authz-check.mjs` extended with the M3 attack matrix (checks 14–18): owner
  upload/sign happy path; foreign-storage-path CHECK rejection; cross-user document
  select/insert/update/delete denial including `uploaded_by` spoofing; storage isolation —
  upload into A's folder, replace via upsert, download, list, sign, delete, and anonymous
  download all denied for user B, with an admin check that A's object survived the attack; and
  the cascade check now verifies documents die with their course.

### Storage architecture (spec D, L, O)

- **Bucket:** `course-materials`, private.
- **Object path convention (ADR-0008):** `user_id/course_id/document_id/filename` — the first
  segment makes per-user storage policies trivial, the second lets M4 workers locate a course's
  corpus, the third guarantees uniqueness, and the filename keeps downloads human-readable
  (sanitized: control/path characters stripped, length capped).
- **Signed URLs only** (TTL 300 s), created on demand when the student taps "Open"; never
  persisted anywhere. The database stores the storage key, not a URL.
- **No service-role key anywhere in the client.** The app uses only the anon key + the user's
  session; the service-role key exists only in the local authz harness which never ships.

### Clean abstractions (spec O)

- `packages/domain/materials.ts` — pure, platform-free: supported formats + MIME map,
  `validateMaterialFile` (extension **and** MIME cross-check; tolerates missing/generic MIME,
  rejects contradictions), `sanitizeMaterialFilename`, `buildStorageKey`, the processing state
  machine (`canTransitionStatus`), size limit + labels + `formatBytes`. 11 unit tests.
- `apps/app/src/features/materials/`
  - `documentsApi.ts` — document repository (list, create row, mark uploaded/failed, update
    type, delete row, find duplicate).
  - `materialStorage.ts` — storage service (upload with `upsert:false`, remove, signed URL).
  - `contentHash.ts` — `sha256Hex` behind a feature-detected WebCrypto interface.
  - `filePicker.ts` — `pickMaterialFile()` wraps `expo-document-picker` behind a clean
    interface returning `{ name, size, mimeType, bytes }` or `cancelled`; web and native both
    yield an `ArrayBuffer`, so everything above the picker is platform-agnostic (spec G).
  - `uploadService.ts` — orchestrates the flow (below), plus `notesToFile` (pasted notes →
    private .txt material) and `deleteMaterial` / `removeCourseMaterialObjects`.

### Upload flow and order of operations (spec F, Q; ADR-0008)

1. Validate (extension, MIME, size) in the domain layer — clear, human errors, no raw backend
   text.
2. Duplicate check (below); if a match is found, stop and ask the student.
3. INSERT the document row at status `uploading` (the DB assigns the id the path needs).
4. Upload the bytes to `user_id/course_id/document_id/filename`.
5. UPDATE the row with the storage key and status `uploaded`.

A failure after step 3 marks the row `failed` with a friendly message; the row is visible in the
Materials list with a "Try again" action (re-pick, re-upload, then remove the failed row). The
upload button disables and relabels ("Uploading…") for the whole flight and the handler guards
re-entry, so repeated taps cannot create duplicates. Progress is shown as an indeterminate
"Uploading…" state — Supabase's JS upload API does not expose byte progress, so a percentage
would be fake (documented limitation).

### Deletion (spec I)

Order: storage object first, then the database row. Both halves are idempotent (removing a
missing object is a no-op), so a partial failure — object gone, row still present — is recovered
by simply deleting again. The reverse order could leak an orphaned, unreferenced object with no
UI to reach it. Deletion always requires an explicit inline confirmation stating the file is
removed permanently. Deleting a **course** first removes all of its material objects
(`removeCourseMaterialObjects`), then deletes the course (rows cascade via FK). **M4/M5 note:**
when derived artifacts exist (chunks, embeddings), document deletion must cascade to them —
the `documents` FK cascade plus this object-removal step is the pattern to extend.

### Duplicate detection (spec J)

- **Web:** SHA-256 of the file bytes via WebCrypto, stored in `content_hash`, matched per
  course before upload.
- **Native (documented deferment):** Hermes does not provide `crypto.subtle`, and a JS-side
  hash of a 50 MB file would be slow and fragile. `sha256Hex` returns `null` on native and the
  duplicate check falls back to `original_filename + file_size` per course. The `ContentHasher`
  interface means a native implementation (e.g. `expo-crypto` digest of the byte stream) can
  slot in later without touching callers.
- Either way, a suspected duplicate is never silently re-uploaded or silently dropped: the
  student sees "already uploaded as …" and explicitly chooses "Upload anyway" or cancels.

### File formats and size limit (spec A, E)

- Supported: **PDF, PPTX, DOCX, TXT** — the modern formats M4's extraction pipeline will
  handle. Legacy binary `.doc`/`.ppt` are rejected with a clear message; their parsing story is
  a rabbit hole with near-zero occurrence among current students.
- Limit: **50 MiB** (`DEFAULT_MAX_MATERIAL_BYTES`, one configurable constant, mirrored in the
  bucket's `file_size_limit`). Rationale: the largest realistic lecture deck / scanned chapter
  is well under 50 MB; larger files are almost always video (out of scope) and would hurt
  mobile upload reliability and storage cost. Errors say the limit plainly.

### Processing status model (spec B, P; ADR-0008)

```
uploading → uploaded | failed
uploaded  → queued            (M4 enqueues here — the hook boundary)
queued    → processing
processing → ready | failed
failed    → uploading | queued   (retry)
ready     → (terminal)
```

Only `uploading`, `uploaded`, and `failed` actually occur in M3; the rest are defined (and
transition-tested) so M4 plugs into `uploaded → queued` without schema or state-machine churn.
There is no fake worker, no simulated processing, no dead code pretending to be M4.

### PHI warning (spec M)

The Add Material screen leads with a prominent card: do not upload patient-identifying
information or PHI — lecture slides, study guides, notes and educational cases belong here,
real patient records do not. Concise, visible, not buried in fine print.

### UI (spec F, H)

- **Materials screen** (`/course/[id]/materials`): loading, error-with-retry, empty state
  ("Add your first material"), and cards showing original filename, type label, size, upload
  date (student's timezone), and status (failed in red with its message). Tapping a card
  expands metadata with **Open** (signed URL), **Try again** (failed only), and **Delete**
  (confirmed). Two-column layout on wide screens.
- **Add Material screen**: PHI card, file/notes mode toggle, file picker with type chips
  (radio semantics, accessible labels), notes title + multiline text ("saved as a private text
  file in this course"), duplicate confirmation, disabled "Uploading…" button in flight,
  friendly errors for unsupported/oversize/empty/cancelled/network cases.
- Course detail gained a **Materials** button, and its delete-course confirmation now mentions
  uploaded materials.

### Tests (spec S)

- **Domain (11 new, 41 total in `@avidia/domain`):** format acceptance, legacy rejection,
  MIME contradiction vs. generic-MIME tolerance, size limits (default, custom, null), the full
  state machine including no-shortcut assertions, storage-key convention, filename
  sanitization (path traversal → harmless), extension case-insensitivity, `formatBytes`.
- **App (14 new, 67 total):** Materials screen empty/list/delete-confirm/cancel/retry flows;
  Add Material PHI warning, validation errors, cancelled pick, successful upload with chosen
  type, invalid outcome, duplicate → "Upload anyway" → `allowDuplicate: true`, failure
  message, **double-submit prevention** (second tap while in flight performs zero extra
  uploads), pasted notes stored as a `.txt` material with `document_type: 'notes'`.
- **Authz harness:** M3 checks 14–18 as described above (runs against a live project; skips
  cleanly without secrets).

### Telemetry (spec R)

No telemetry/analytics abstraction exists in the repo. Per spec, none was invented for M3;
upload success/failure instrumentation waits until an observability layer is introduced
deliberately.

## Known limitations

- **No live Supabase project yet** (founder setup still pending, as at M1/M2). Migrations
  0001–0003 are ready to apply; the authz harness and the 17 manual verification steps that
  need a real backend are blocked until then.
- **No real upload progress percentage** — indeterminate "Uploading…" only (API limitation,
  honest by design).
- **Native content hashing deferred** — name+size duplicate fallback on iOS/Android until a
  native SHA-256 implementation is slotted into the `ContentHasher` interface.
- **No storage-level orphan sweeper** — deletion ordering makes orphans unlikely, but a
  periodic reconciliation job (storage ↔ documents) is a sensible later hardening task.

## M4 boundary

M3 ends with materials at rest at status `uploaded`. M4 (per Playbook: ingestion) begins at the
`uploaded → queued` transition: text extraction for PDF/PPTX/DOCX, chunking with provenance,
and retry handling — none of which exists, is stubbed, or is simulated in this codebase today.
