# M8 — Adaptive mastery engine and intelligent study scheduler

Date: 2026-08-13. Builds on M7 (`0af9961`).

Scope note: THE LLM IS NOT THE MASTERY ENGINE. Every mastery number, state,
review time, priority and recommendation in this milestone is computed by
deterministic, versioned, unit-tested code — SQL inside the submit RPC and
the pure `@avidia/mastery` package — never by an AI provider (spec core
principle, V, AE). No mastery data ever leaves the student's own database
rows. This milestone deliberately ships the MINIMAL dashboard (spec AF);
the full progress/analytics experience is M9+ and was not built (spec AO).

## What shipped

- **`@avidia/mastery` package** — a crypto-free, dependency-light pure
  engine the app imports at the package root:
  - `config.ts` (spec AJ): every constant in ONE file — gain/drop rates and
    caps, difficulty/cognitive/confidence weight tables (spec F/G/H),
    `RESPONSE_TIME_FACTOR = 1.0` (excluded in v1, documented, spec I),
    review intervals `[24, 72, 168, 336, 720]` hours (spec K), state
    thresholds (spec Q), exam-urgency steps (spec L), diversity bounds
    (spec W), `QUESTION_SUPPLY_LOW_THRESHOLD` (spec Y),
    `MASTERY_ALGORITHM_VERSION = 1` (spec AA).
  - `update.ts` (spec D/E/F/G/H/R): pure
    `updateMastery(previous, performanceEvent) → { aggregate, delta, … }`
    with bounded diminishing gains, capped single steps, confidence
    calibration that never punishes honesty, and misconception severity
    from repeated confident-incorrect answers. No DB access, no clock
    reads — `answeredAt` drives all timestamps.
  - `states.ts` (spec B/C/J/Q): evidence band vs. review urgency kept
    separate; no evidence ⇒ `unassessed`, never "needs review"; overdue
    overlays `due_for_review` without erasing evidence.
  - `examUrgency.ts` (spec L/AI): timezone-correct calendar-day distance to
    M2 exam dates via the SAME domain utility the countdown UI uses, so
    scheduling and display can never disagree. Exam scope is course-wide in
    v1 with a `conceptIds` manual-adjustment path (spec M).
  - `priority.ts` + `recommend.ts` (spec N/O/P/S/T): the versioned priority
    function (exam relevance × weakness × forgetting risk × emphasis ×
    misconception × transfer need), reason codes
    (`unassessed/low_mastery/review_due/exam_soon/recent_error/
high_course_emphasis/question_supply_low`) that ARE the explanation
    (spec T — no LLM), mastery-appropriate target question characteristics
    (spec U), and deterministic ranking with stable tie-breaks.
  - `selectQuestion.ts` (spec U/V/W/X/Y/AN): seeded deterministic adaptive
    ordering over the PERSISTED M7 bank — unseen first, characteristic
    match next, diversity caps (max 2 consecutive, ≤50 % share), graceful
    relaxation when supply runs out (`question_supply_low` is a reason
    code, never an AI call).
  - 90 package tests across 8 suites, including simulated students A–G
    (spec AK) with per-step invariants and the five golden cases (spec AL).
- **Migration `0008_mastery_and_scheduling.sql`** — `concept_mastery`
  (one aggregate row per user × course × concept, spec A/AM),
  `mastery_events` (append-only audit of every update with
  `unique(attempt_id)` idempotency, spec Z/AC), both select-own-only with
  NO client write path of any kind (spec AD), and a replaced
  `submit_question_attempt` that transactionally applies the SAME v1
  arithmetic (constant-for-constant mirror of `config.ts`) after scoring:
  `SELECT … FOR UPDATE` serializes concurrent updates, and a double submit
  aborts at the attempt's unique violation BEFORE any mastery arithmetic
  (spec AC). The RPC's return value gains a backward-compatible `mastery`
  key. `study_sessions` now accepts session_type `'adaptive'`.
- **Domain** — mastery states (`unassessed/needs_review/developing/strong/
due_for_review`) with non-stigmatizing labels ("New", never "failing",
  spec C/Q) and recommendation reason labels; a test bans stigmatizing
  words and digits in student-facing labels (81 domain tests).
- **App** — `studyApi.ts` (owner-scoped reads + pure snapshot assembly the
  engine consumes, spec AH), the minimal study dashboard (spec AF: next
  exam countdown, ONE recommended action with honest reasons, concepts
  grouped by coarse state — counts only, no percentages, spec AG/B),
  adaptive session mode in the existing practice flow (session-id-seeded
  deterministic selection, works with zero AI configuration, spec V), a
  Study tab course chooser, and a Study button on the course screen.
  The UI never calculates priorities — it renders engine output (spec AH).
- **Authz harness** — M8 checks 41–44: RPC-created aggregates verified
  against the exact v1 arithmetic; one audit event per attempt; refused
  double-submit never double-updates; owner-only reads; zero client write
  paths; adaptive session type accepted/unknown rejected; course-delete
  cascade covers both new tables.

## Manual validation (spec AR)

With a course that has processed materials, questions, and an exam date:

1. Open a course → the new **Study** button appears; the Study tab lists
   your courses.
2. Open Study with NO attempts yet → every concept shows **New**, the
   recommendation reason includes "You haven't practiced this yet", and no
   number or percentage appears anywhere.
3. The next upcoming exam shows with the same countdown wording as the
   course screen (timezone-correct).
4. Start an adaptive session → it begins instantly with no AI configured.
5. Answer a question correctly with "Pretty sure" → finish → the concept
   moves toward **Developing**; the dashboard shows states, never scores.
6. Answer several questions on one concept incorrectly → it shows
   **Needs review** and becomes the recommended next action with
   "Recent answers suggest a gap here".
7. Answer incorrectly with "Certain" repeatedly → the recommendation
   persists (misconception signal raises priority); wording stays
   non-judgmental.
8. Mark confidence "Guessing" on correct answers → progress is slower and
   the review schedule does not advance (verify `review_stage` stays 0 in
   `concept_mastery`).
9. Submit the same question twice in one session (double-tap/replay the
   RPC) → second call errors; `concept_mastery.attempts_count` rose once.
10. In SQL: every attempt has exactly one `mastery_events` row;
    `mastery_before/after` chain correctly; `algorithm_version = 1`.
11. In SQL as user B (or anon): `select * from concept_mastery` and
    `mastery_events` return zero rows; inserts/updates/deletes error.
12. With an exam tomorrow, a weak concept ranks first with "Relevant to an
    upcoming exam"; delete the exam date → the ranking softens but the
    weakness still surfaces.
13. Set your profile timezone to Pacific/Honolulu → exam countdown and
    urgency agree with the course screen (no hard-coded Central).
14. A concept with fewer than 3 unseen questions shows/behaves with
    "Limited questions available" — and NEVER triggers an AI call.
15. Practice (non-adaptive) mode still works exactly as in M7 and session
    rows say `practice`; adaptive rows say `adaptive`.
16. Strong concept: 10 confident correct answers → **Strong**; come back
    after the review interval → **Due for review** while the underlying
    evidence stays strong (check `mastery` did not decay in SQL).
17. Refresh mid-session → the same question order resumes (session-seeded
    determinism).
18. Kill network mid-submit → error banner, retry works, no duplicate
    mastery update afterwards.
19. Delete the course → `concept_mastery` and `mastery_events` rows are
    gone; the profile survives.

## Handoff to M9 (NOT implemented, spec AO)

M9 can consume: `concept_mastery` aggregates + `mastery_events` history
(auditable trend data), `rankConcepts` full output (per-factor breakdown in
`factors`), and the `study_sessions.session_type` distinction. Non-goals
left untouched: progress charts/analytics dashboards, gamification, streak
mechanics, pass-probability or exam-readiness predictions, AI study chat.
